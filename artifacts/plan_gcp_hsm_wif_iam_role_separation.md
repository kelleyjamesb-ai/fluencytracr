# Section 7.3 plan — GCP HSM, WIF, IAM, and role separation

## Objective

Close only the docs-only security-authority contract required by Section 7.3 of `docs/contracts/canonical-inference-gcp-runtime-candidate/README.md`. Define deterministic policy/evidence shapes, hashes, transitive role separation, future lifecycle proofs, and fail-closed decisions. Keep runtime authority held and all runtime/GCP actions unauthorized.

## Base and dependency boundary

- Branch base: Section 7.2 commit `f9db14dc4530266e95b4c7f3176a2eca6b9c72a6`.
- Section 7.3 semantically depends only on the frozen Section 7.1 provider vocabulary plus a new Section 7.3 public-provider evidence/revalidation bundle.
- Section 7.2 is a compatibility boundary, not a Section 7.3 hash dependency. No Section 7.2 object/profile/control/instance hash or value enters a Section 7.3 hash preimage. Section 7.4/7.7 own later reconciliation.
- Section 7.3 does not define receipt signature preimages or signer acceptance. Section 7.4 owns those semantics.

## Acceptance criteria

1. **Provider claim closure:** Bind exact hashes for all four Section 7.1 provider artifacts and inherited Confidential Space claim IDs; add exact Section 7.3 public-source claims and an offline-replayable recovery bundle for Confidential Space WIF, subject-token claims, direct federated Cloud KMS support, HSM protection/non-exportability/attestations, asymmetric signing, manual asymmetric-key rollover, IAM role separation, policy evaluation, and audit behavior. Distinguish subject-token `aud`, STS endpoint, and provider-resource exchange audience. Missing sources or source drift HOLD; conflicting current documentation or unsupported claims reject. Offline byte replay classifies absence, hash failure, or an unreplayable compiled evidence window as drift; the reject branch requires reviewed current provider documentation.
2. **Artifacts:** Add a contract README, machine-readable security policy/evidence contract, provider source/claim/revalidation manifest, role/capability matrix, synthetic canonical vectors, offline verifier, focused tests, and a strict OpenSpec change.
3. **Project roles:** Define five pairwise-distinct symbolic project roles—security policy, key custody, build, runtime, and audit—as a design contract, not a provider requirement. Actual identities remain absent and require restricted external evidence.
4. **Privacy-safe identity references:** Contract artifacts use random context-bound opaque aliases generated independently of project/principal/account identifiers. Plain/dictionaryable hashes and identifier-bearing locators reject. Actual raw project/principal/policy/log mappings remain in a separately governed restricted evidence boundary and never enter runtime/model/customer artifacts.
5. **Digest mode selected:** WIF admission is image-digest based. Confidential Space signed-image launch mode, `tee-signed-image-repos`, and signature-claim admission are prohibited because Section 7.1 does not establish digest/signature claim coexistence. Image signing is detached provenance checked before deployment and does not replace the required token image digest.
6. **WIF admission:** Require an active workload identity pool and OIDC provider with exact nondeleted lifecycle state and `disabled=false`; missing, disabled, deleted, unknown, or contradictory state HOLDs. Require Google Cloud Attestation issuer, default subject-token audience `https://sts.googleapis.com`, separately typed STS endpoint and provider-resource exchange audience template, direct resource access, no service-account impersonation, exact mapping AST, and exact condition AST covering TDX hardware, `CONFIDENTIAL_SPACE`, production debug status, `STABLE`, secure boot, runtime project/zone, immutable image digest, no command/environment override, restart `Never`, and closed monitoring posture. Missing/type/alias/unknown claims reject.
7. **Alternate credentials:** Attached VM identities, metadata-server access tokens, user-managed service-account keys, `actAs`, `getAccessToken`, `signBlob`, `getOpenIdToken`, Token Creator, and impersonation paths must have no effective route to either signing key or authority mutation. `google_service_accounts` values are never admitted; future evidence retains only closed alternate-credential denial results. Same-context alternate-credential negative canaries are mandatory before any later activation.
8. **Principal/capability separation:** Define context-bound opaque role aliases for runtime signer, image signer, image builder, image publisher, deployer, key-lifecycle admin, key-destruction approver, key-destruction executor, KMS-IAM admin, WIF-provider admin, verifier, security auditor, audit-router admin, and audit-retention custodian. Every pair of transitive controller sets must be disjoint. Role aliases are injective within one evidence bundle. Builder/publisher/signer, key/IAM/WIF admins, router/custodian, deployment, verification, and audit are distinct.
9. **Transitive authority universe:** Effective-access evidence must close organization/folder/project/key ancestry, inherited and conditional bindings, custom-role definitions, groups/domains, service agents, attached identities, WIF principal sets, deny/PAB policies, owner/editor grants, role mutation, WIF-provider mutation, KMS-IAM mutation, audit mutation, and actual controllers. A machine-computed least fixed point starts from a sorted unique typed credential-control edge inventory, recursively expands every direct and indirect credential-controller edge, requires reported controller sets to equal the derived closure, rejects every cycle, records a domain-separated completeness witness, and rejects caller-asserted completeness. Every role pair must have disjoint transitive credential-controller sets. A separate complete authority-mutator influence graph records typed internal and external WIF/key/IAM/audit/owner/editor/custom-role/group/IdP/service-agent/recovery mutation power; every mutator must be externally proven dormant and any activation invalidates evidence. Groups/domains and unknown/unviewable policies are prohibited for signing paths. An incomplete universe HOLDs.
10. **Standing access versus mutation power:** No admin/deployer/auditor has standing `useToSign`. KMS-IAM/WIF/key admins are explicitly `AUTHORITY_MUTATOR` roles, not claimed unable to self-escalate. Runtime authority can only be considered later while every mutator is externally proven dormant. Any policy, role, provider, key, project, or audit mutation immediately invalidates evidence and holds authority pending complete re-proof.
11. **HSM key generations:** Define distinct image-provenance and runtime-receipt CryptoKeys. Each future generation must be Google-generated, non-exportable, HSM-attested, `protectionLevel=HSM`, `purpose=ASYMMETRIC_SIGN`, `algorithm=EC_SIGN_P256_SHA256`, exact version `1`, exactly one version total, `ENABLED`, and bound to an SPKI/public-key fingerprint plus HSM-attestation commitment. Imported/external/software keys, extra versions, primary/alias resolution, and automatic rotation fields reject.
12. **Least privilege:** Runtime and image signers have only `cloudkms.cryptoKeyVersions.useToSign` on their distinct enabled CryptoKeys. Verifiers have only public-key retrieval. Key lifecycle, KMS-IAM, WIF-provider, build/publish, deployment, routing/retention, and audit capabilities remain separately scoped. Unlisted permissions reject.
13. **Detached image provenance:** Define—but do not execute—a deterministic future Simple Signing payload byte contract over the immutable OCI digest. Live evidence must cross-bind the exact OCI digest/HMAC reference commitment, purpose, generation alias, version `1`, algorithm, SPKI digest, payload-schema hash, canonical-payload hash, signature and payload/privacy verification receipts, verifier/time, deployment candidate/attempt, gate-consumption commitment, verification result, and deployment-gate result. Runtime-approved privacy/verifier/gate policy lists remain empty. Cosign interoperability remains unproven until separate conformance; Binary Authorization is not claimed to enforce Compute Engine/Confidential Space deployment.
14. **Policy and evidence hashes:** Define an acyclic graph: provider revalidation → `security_authority_policy_hash` → `security_authority_evidence_snapshot_hash`. Policy, absent-evidence, and closed live-evidence nested schemas, synthetic test vectors, and actual admission domains are separate. Synthetic validation proves structure/derivation only—not authenticity, completeness, HMAC, signature validity, or approval. Runtime-approved policy/evidence lists remain empty; nonempty placeholder lists reject.
15. **Effective-access proof:** Compile and require exactly once every role × `{image key, runtime key}` × `{useToSign, viewPublicKey}` tuple plus every alternate-credential route. Require policy/role/provider/key etag commitments, same-valid-context allowed and denied synthetic canary schemas, exact enabled resource/principal/permission binding, observed denial cause, and audit correlation. Do not rely on Policy Troubleshooter for workload identities or on unproven IAM-deny support for `useToSign`; `UNKNOWN`, unexpected success/failure, ambiguous network/token/key-state failure, stale snapshot, or missing correlation HOLDs.
16. **Authority-held rollover state machine:** Future rollover creates a distinct CryptoKey generation rather than an extra usable version and records every ordered state-prefix transition with strictly increasing observation times. `HOLD_PREPARE` → verify HSM attestation/public key → freeze new policy → revoke old signer grant → prove old denial → grant new key → prove new allow and cross-key denies → freeze evidence → only a later Section 7.7/7.8 decision may leave HOLD. Never approve two generations simultaneously. Compromise skips normal cutover and holds/revokes immediately. Old public-key commitments remain verifier-readable for receipt retention. Destroy/restore requires separately authorized approver/executor evidence and cannot precede receipt-retention expiry.
17. **Audit interface, not persistence selection:** Section 7.3 defines the complete authority-operation inventory and immutable evidence interface; Section 7.5 must map each operation to exact provider service/method/log semantics with fresh source revalidation for STS/WIF, IAM/custom roles/deny/PAB, KMS policy/lifecycle/signing/public-key operations, image provenance publication, alternate credentials, and audit configuration/routing/retention mutations. Section 7.5 owns the actual logging/sink/bucket/persistence choice; live evidence must bind an approved Section 7.5 contract/decision/method map and an audit window encompassing every relevant canary/provenance/rollover event. The approved list remains empty. Raw logs, principal emails, IPs, policies, signatures, and account IDs stay external; only context-bound aliases, high-entropy bundle commitments, closed counts/windows, and restricted opaque references may cross.
18. **Total decision precedence:** Privacy/boundary leakage → provider conflict/unsupported claim → provider source unavailable/drift → role/authority-universe collision → key/WIF/policy mismatch → incomplete or stale evidence → `GCP_SECURITY_AUTHORITY_CONTRACT_CLOSED_EVIDENCE_ABSENT_RUNTIME_AUTHORITY_HELD`. Unknown values reject or HOLD exactly; no override.
19. **No additive authority:** Section 7.3 policy/evidence objects, hashes, states, vectors, or composition with any earlier/later object have `authority_effect=NONE`. Execution remains impossible until Section 7.7 integration GO, Section 7.8 exact qualification, and a fresh human execution authorization. Synthetic hashes can never satisfy live evidence.
20. **Privacy/governance:** No customer data, raw GCP policies/logs/tokens, account/email/person identifiers, private/raw/wrapped key bytes, real signatures, credentials, prompts, model material, new canonical events, suppression reasons, tunable product thresholds, or admin overrides.
